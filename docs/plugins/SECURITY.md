# Plugin security: what is enforced

Plugins are executable code. In this version they are meant to be **locally developed and reviewed by you**. Don't run plugins from sources you haven't read. Nothing here makes an arbitrary third-party plugin safe.

## Not enforced, or not verified yet

- **The Chromium sandbox can have bugs.** The OS-level sandbox is what stops a renderer exploit from reaching the system. The automated suite runs as root in a Linux container with `--no-sandbox`, so it checks JS-level isolation and network blocking but **not the OS sandbox itself**. On Windows the sandbox is on by default. Checking it there is in the manual checklist.
- **CPU and memory** are limited only by timeouts and killing the window, not by quotas.
- **Validation can't judge intent.** A plugin can misuse what it was granted: a plugin with `"*"` network can send whatever its tools receive to any public host. Review the code and the permissions.
- **Model-level authorization.** Write tools ask you, but read tools don't. A read tool with network access can still send data (for example, a query) to its allowed hosts.
- **Custom-scheme links.** `ctx.openExternal` hands an approved custom-scheme link (such as `spotify:`) to whatever app Windows has registered for that scheme. Custard allows only plain URL characters and refuses known risky schemes. It can't know how the handler parses the link, and %-escapes are decoded there. Approving a scheme means trusting that app's handler. Only schemes on Custard's vetted list can be declared, because any app can register a scheme and some handlers write files or start tools (for example `obsidian://` can write vault notes). Only write tools can open links, so a read tool can never open one without an approval.
- **File-check races.** Paths are checked right before each operation. Another program swapping a folder for a link between the check and the write isn't prevented.
- **DNS prefetching** in the plugin window wasn't tested separately. Its requests carry no plugin-chosen data beyond host names.
- **Packaged builds** haven't been built or tested. Development (`npm run dev`) is the supported setup.

## What validation checks, and what it can't

Validation checks:

- manifest fields and types
- API version
- schema keywords
- tool names, length and collisions
- that `entry` and `instructions` exist inside the folder
- that the code bundles using only allowed imports

The test run also loads the plugin in a sandbox and checks that every declared tool has a handler.

None of that shows the code is correct or honest. That is why you review the diff and the permissions, and why write tools ask.
